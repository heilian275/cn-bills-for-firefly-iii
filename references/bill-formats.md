# 支付宝与微信账单格式

两个平台导出的官方账单格式稳定，但各有几个不明显的坑。下面的商家名、订单号、金额都是虚构示例。

支付宝是 csv，微信是 xlsx（从 zip 解压后得到）。两边的列名和编码不一样，不要拿一套解析套两个平台。

## 支付宝「交易明细证明」

- 文件名：`支付宝交易明细(YYYYMMDD-YYYYMMDD).csv`。
- 编码是 gb18030，不是 UTF-8。按 UTF-8 读会直接报错。
- 表头在第 24 行（从 1 数）或第 23 行（从 0 数）。前面是用户信息区，后面有「共 N 笔」的汇总行。
- 12 列：`交易时间 / 交易分类 / 交易对方 / 对方账号 / 商品说明 / 收/支 / 金额 / 收/付款方式 / 交易状态 / 交易订单号 / 商家订单号 / 备注`。

### 支付宝的坑

1. 数据行里可能有逗号，外面用引号包着。不能用 `split(",")` 解析数据行，要用 csv 模块，比如 `next(csv.reader(io.StringIO(line)))`。
2. 订单号列末尾有 `\t`，比较或拼 external_id 前先 strip。有些环境整行都带不可见空白，逐字段 strip 最保险。
3. 金额可能不是纯数字：带 `¥` 前缀，或者为空。解析时做容错。
4. 「收/支」有三种值：`支出`、`收入`、`不计收支`。「不计收支」大多是资金流转（还款、提现、充值），不是消费也不是收入。
5. 复合支付的收/付款方式写成 `主卡&优惠名`，例如 `某银行储蓄卡(1234)&平台立减金`。`&` 前面是银行账户的形态，后面是优惠名。
6. 退款单的订单号从原单派生：原订单号 + `_` + 退款流水号。比如 `...42000000_13120000...` 退的是 `...42000000`。
7. 「对方账号」列：机构是脱敏的邮箱或手机号，个人商家经常是 `/`，也就是没有。
8. 状态有 `交易成功`、`支付成功`、`交易关闭`、`等待确认收货` 等。`交易关闭` 表示没有资金流。
9. 同一个商家订单号可能拆成多行，比如一单多件、¥0 子行。判断结构要看商家订单号的前缀段。

## 微信「支付账单流水」

- 文件名：`微信支付账单流水文件(YYYYMMDD-YYYYMMDD)_<时间戳>.xlsx`，zip 解压后得到。
- xlsx，用 openpyxl 读：`load_workbook(path, data_only=True)`。
- 表头在第 18 行（从 1 数）或第 17 行（从 0 数），数据从下一行开始。
- 11 列：`交易时间 / 交易类型 / 交易对方 / 商品 / 收/支 / 金额(元) / 支付方式 / 当前状态 / 交易单号 / 商户单号 / 备注`。

### 微信的坑

1. 没有「对方账号」列，这一点和支付宝不同。
2. 「交易类型」有 `商户消费`、`转账`、`扫二维码付款`、`淘宝平台-退款` 等。退款是独立类型，退款单和原支出单分两行。关联依据是金额一致、同一天、原单状态为「已全额退款」。这是客观状态字段，不靠推断。
3. 「支付方式」为 `/` 的行多是人对人转账。微信侧复合支付少见。
4. 金额列是数值型。转成字符串时注意 `16.99` 和 `16.990000000000` 的差别，导入前格式化成两位小数。
5. 「商品」列里常有对方名或商户单号。description 怎么写，看用户实例里既有交易的风格，字段说明见 `references/mapping-json.md`。

## external_id

- 支付宝：`alipay:` + 交易订单号。
- 微信：`wechat:` + 交易单号。
- 同一批保持一致，也要和库里已有的格式一致。查重和幂等依赖它。

## 其他

- 解析大文件时只把需要的列带进上下文，逐笔的全字段明细留在脚本或文件层。
- Windows 控制台打印中文可能乱码。脚本里已经做了 `sys.stdout.reconfigure(encoding="utf-8")`；调用环境还有问题就自行适配。
